## 使用门槛

requirement-analyst 判定 `ui_relevant: false` 时，本文件保持为空骨架即可，后续阶段全部跳过 UI 相关检查。
判定为 `true` 时，**以下 4 个章节为必填**（缺任一则 HG-1 不得通过）：

1. §1 页面 / 路由清单
2. §3 布局骨架（桌面 + 移动各一份 ASCII）
3. §5 交互状态矩阵（含 loading / empty / error）
4. §6 响应式行为（逐断点）

## 三条铁律

| 铁律 | 内容 |
|:--:|------|
| 1 | **禁止抽象形容词** —— 不写「美观/现代/简洁/响应式适配」，写具体值（色值、px、断点行为） |
| 2 | **布局必须有 ASCII 骨架** —— 纯文字描述布局必然歧义，骨架是让 implementer 停止即兴发挥的最低成本手段 |
| 3 | **状态必须穷举** —— 「列表页」不是一个状态，是 default / loading / empty / error 等一组状态 |

## 维护规则

### 谁写入
- **requirement-analyst**：需求分析阶段首次填写本文件（主体内容）
- **plan-generator**：补充「组件清单」的技术落地路径与响应式断点来源；**不修改需求语义**
- **Cursor Agent**：HG-1 / HG-1.5 用户确认后登记确认状态

### 谁读取
- **plan-generator**：设计 design system 与页面 override 的输入
- **implementer**：写 UI 代码前的界面契约（禁止偏离 §3 骨架与 §5 状态矩阵）
- **reviewer-visual**：视觉审查的对照基准
- **verifier**：视觉验证的对照基准（结合 `visual-baseline.md` 的冻结 token）

### 变更规则
- HG-1 通过后，§3 布局骨架与 §5 状态矩阵的**语义变更**必须回到用户确认
- 纯技术细节补充（如断点来源、组件路径）可由 plan-generator 直接追加，无需重新确认
- 本文件与 `requirements.md` 冲突时，以 `requirements.md` 的 AC 为准（AC 是验收契约）
