## 产品目标

本工作流的**核心交付物**是**可重复运行的真机闭环验证基座**（复用层 V 冒烟闭环基座：Xvfb + `code` CLI + 截图 + 断言 + journal + 状态记录），并对 vscode-dsh **当前代码真实实现**的每一项功能能力**逐项真机驱动、收集证据**。对每项能力，达成真闭环（实际触发 + 具体结果断言 + 真实截图）则记录「闭环通过」；达不成的，如实登记缺口与原因，汇总后交由后续 feature 补充开发，**本工作流不补齐、不回归**。

## 问题陈述

上一轮 `vscode-dsh-e2e-closure` 以 descoped 关闭：部分能力只写了 manifest steps 却从未真机运行，部分已"验证"的能力实际是空壳（只打开面板 / 只看 DOM 存在 / HTTP 200，未真正触发行为并断言具体结果）。因此本工作流重新聚焦，只做一件事：**搭起可重复运行的真机闭环验证基座**，用它逐项驱动当前代码真实实现的每项能力，能闭环则闭环、不能闭环则诚实登记，替代「面板打开 / DOM 存在 / HTTP 200」这类空壳验证。

## 目标终态

1. 一个**可重复运行的真机闭环验证基座**（命令 + 编排 + journal + 机器可读状态记录 + 截图），能对「当前代码真实功能能力清单」逐项真机驱动。
2. 清单中每一项能力都有一份「真机驱动 + 证据 + 结论」，结论明确为「闭环通过」或「未闭环」。
3. 判定为「未闭环」的能力（缺实际触发 / 缺具体结果断言 / 缺真实截图），其缺口与原因**如实登记**在 `tech-debt-registry.md` 与验证报告，汇总后交由后续 feature 补充开发。
4. 既有回归测试（单元/协议层与真机冒烟）在交付后保持全绿。

## 目标用户

- **vscode-dsh 维护者 / 贡献者**：需要一份可重复运行的真机闭环，判断当前代码真实实现的能力是否在真机 Extension Development Host 中真正可用。
- **发布/验收流程**：发布前需要真机证据，替代「DOM 存在 / HTTP 200」这类弱证据。

## 核心场景

1. **S-1 全链闭环**：维护者运行一条真机闭环命令，按「当前代码真实功能能力清单」逐项在真机 EDH 中驱动、断言、截图，产出机器可读状态记录 + 截图证据。
2. **S-2 能力单项复验**：维护者只复验某一项能力（如 editor-chat-panel 的 React SPA 主呈现路径），运行对应闭环子集，获得截图 + 断言，无需跑全量。
3. **S-3 空壳复核**：维护者对历史标记"已验证"的能力，按真闭环标准复核，识别出「实际未闭环」的能力并**登记**（不补齐）。

## 验收标准（EARS 格式）

### 功能区域 1：真闭环判定标准（核心语义）

- **AC-1**（普遍型）：系统 **必须** 以「三项同时满足」作为一项能力被判定为「真机闭环验证通过」的唯一标准——① 在真机 Extension Development Host 中**实际触发**该行为；② 存在**针对具体结果的断言**（判定者读到该断言能明确给出 ✅ 或 ❌）；③ 存在**真实桌面截图**作为证据。**该三条是「判定一项能力是否已闭环」的标尺；本工作流不要求清单中每项能力都三条齐备——未齐备的按 AC-15 登记为「未闭环」。**

- **AC-2**（不期望行为型）：**如果** 某项能力的断言仅能证明「面板已打开 / DOM 节点存在 / HTTP 200 / 命令已注册」而未证明具体行为结果，**那么** 系统 **必须** 判定该能力为「未闭环验证」，**不得** 记为「验证通过」。

### 功能区域 2：能力清单来源与覆盖边界

- **AC-3**（普遍型）：系统 **必须** 在设计阶段前委托 workflow 级 code-explorer 对当前代码进行调研，产出一份「真实功能能力清单」，清单中每一项 **必须** 附代码位置证据（`路径:行号`）；该清单是闭环功能覆盖的**唯一依据**。清单 **必须** 同时覆盖「历史标为已验证」与「未验证」两类能力，并按当前代码是否真实实现判定去留；旧 feature 文档的历史功能声明 **只可** 作为候选参考，**不得** 作为覆盖依据。

- **AC-4**（不期望行为型）：**如果** 某项能力被 code-explorer 调研确认已废弃、已被后续工作流推翻或被替代（例如 thin HTML 聊天面板已被 React SPA 取代），**那么** 系统 **必须不** 为其建立真机闭环覆盖，且 **必须** 将其列入「过时功能清单」。

### 功能区域 3：层 V 基座复用与真机证据

- **AC-5**（普遍型）：系统 **必须** 复用 `apps/vscode-dsh/test-scripts/run-layer-v-smoke.sh` 已建立的层 V 冒烟闭环能力（Xvfb 显示解析、Node 引擎解析、沙箱 HOME、凭证门控、`--extensionDevelopmentPath` 启动真机 EDH、层 V 驱动扩展、进程回收），**不得** 从零重建同等的显示/Node/沙箱/凭证/进程逻辑。

- **AC-6**（普遍型）：系统 **必须** 为「真实功能能力清单」中的**每一项能力**产出真实桌面截图（PNG）证据与至少 1 条可独立判定的端到端断言；每条断言 **必须** 验证完整数据路径（操作 → 产品响应 → 截图/日志证据）。

- **AC-7**（状态驱动型）：**在** 一次闭环运行**期间**，层 V 驱动 **必须** 将每一步操作序列与断言结果以机器可读 JSONL 形式**逐步追加**写入 journal（`apps/vscode-dsh/test-artifacts/layer-v/` 下），使得中途崩溃的运行仍能按步骤名定位失败点。

- **AC-8**（普遍型）：系统 **必须** 遵循既有层 V 退出码/结论契约——`0`=PASS、`1`=LINK_FAILURE、`2`=SKIPPED_NO_DISPLAY、`3`=SKIPPED_NO_CREDENTIALS、`4`=HARNESS_ERROR，且结论 **不得** 被合并、降级或在证据不足时猜测。

### 功能区域 4：真实 LLM 与凭证门控

- **AC-9**（普遍型）：系统 **必须** 在涉及聊天、消息往返、流式、Continue、分叉等「模型往返」的能力验证中，使用真实 `DEEPSEEK_API_KEY` 完成真实 LLM 往返；**不得** 以注入/回放/模拟作为这些能力的闭环验证等价物。

- **AC-10**（不期望行为型）：**如果** 运行环境无 `DEEPSEEK_API_KEY`，**那么** 系统 **必须** 以 `SKIPPED_NO_CREDENTIALS`（exit code 3）fail-closed 退出，**不得** 把「无 key 未运行」记为「验证通过」。

- **AC-11**（普遍型）：系统 **必须** 对 editor-chat-panel 的 React SPA 主呈现路径（编辑器区单例 Panel、顶栏多 Tab、历史窗口等当前真实存在的呈现组件）产出真机截图 + 断言，作为其「层 V 真机视觉验证」的闭环证据；该验证 **必须** 融合进本工作流的真机闭环流程，**不得** 单列为独立的偏差修复项。

### 功能区域 5：回归护栏与测试资产归属

- **AC-12**（普遍型）：系统 **必须不** 破坏既有回归——交付完成后，既有单元/协议层测试集（`vitest run apps/vscode-dsh/tests`）与既有真机冒烟/回归脚本 **必须** 全部保持通过，**不得** 引入任何回归。

- **AC-13**（普遍型）：系统 **必须** 将本工作流产出的真机驱动 / 闭环编排作为**验证基础设施**落位到 `apps/vscode-dsh/test-scripts/`（与既有 layer-v 相关文件同处）；**不得** 把 phase 临时验证脚本写入 `apps/vscode-dsh/tests/`（功能单元测试目录）。phase 临时验证脚本 **必须** 放在临时目录，验证结束即删除。

### 功能区域 6：验证问题登记与诚实报告

- **AC-14**（不期望行为型）：**如果** 验证过程中发现某项能力未闭环、断言失败或暴露真实缺陷，**那么** 系统 **必须** 将该问题如实登记（写入验证报告与 `tech-debt-registry.md`），**不得** 通过反复重试、降低断言标准、跳过用例、或其它取巧手段强行使验证「通过」；验证结论 **必须** 如实反映真实状态（PASS / PARTIAL / FAIL）。

- **AC-15**（普遍型）：系统 **必须** 以「可重复运行的真机闭环验证基座」为本工作流的**核心交付物**；对「真实功能能力清单」中的每一项能力，系统 **必须** 逐项真机驱动并给出明确结论——达成真闭环（AC-1 三条齐备）记为「闭环通过」，未达成记为「未闭环」并登记「缺哪一条 + 缺口原因 + 建议由何种 feature 补充」；**不得** 在本工作流内通过修改产品代码、反复重试或放宽断言来补齐缺口，缺口汇总后交由后续 feature 补充开发。

## 风险/假设

- **假设 A1**：Xvfb + `code` CLI 已就绪，可直接复用 `run-layer-v-smoke.sh`，无需重新调研显示/Node 解析。
- **假设 A2**：产品代码已实现，本工作流只新增验证驱动代码与编排，不修改产品功能代码。
- **假设 A3**：偏差 5 / 偏差 6 已修复合入，本工作流在包含这些修复的代码基线上运行，无需重复修复。

- **风险 R1（运行时长）**：层 V 真机运行单次耗时长，全量闭环耗时长，需在 Phase 拆分时考虑分批/并行。
- **风险 R2（截图断言易抖动）**：真机截图受窗口尺寸、字体渲染、X 显示差异影响，断言应以「关键区域存在 + 元素非退化」为主，避免逐像素比对。
- **风险 R3（弱证据惯性）**：历史"验证"多为弱证据，复核时可能发现大量「实际未闭环」的能力，导致返工面扩大；需在 Phase 拆分时预留复核与补齐的时间。

## 建议的 Phase 拆分方向

> 仅供 plan-generator 参考，非权威拆分。

1. **代码调研 + 真实功能能力清单**：workflow 级 code-explorer 调研当前代码，产出「真实功能能力清单」+「过时功能清单」，作为后续所有覆盖的依据。
2. **闭环基座 + 单能力打样**：复用 `run-layer-v-smoke.sh` 基座，先用 editor-chat-panel 的 React SPA 主呈现路径打样「操作序列 + 截图 + 断言」范式。
3. **逐能力真机驱动**：按打样范式为清单中其余真实能力逐项真机驱动 + 断言（无依赖关系的能力可并行；能闭环则闭环，不能闭环则登记为「未闭环」）。
4. **全链编排 + 回归护栏**：一条命令串起全链闭环，产出统一状态记录与 artifact-index，并跑既有回归护栏。
