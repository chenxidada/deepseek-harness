## 2. 关于截图：为什么「有截图」不使本视角升级为适用

本 Phase 的产物目录中**确实存在截图**：

```text
$ ls -la apps/vscode-dsh/test-artifacts/layer-v/
step-1-host-started.png          （128828 bytes）
... （step-2..step-5 各一张，AC-26 要求共 5 张）
layer-v-status.json / layer-v-report-meta.json / layer-v-log-evidence.json / ...
```

这些截图**不是视觉设计交付物**，而是**冒烟测试的界面证据**。理由如下，均来自 spec 原文：

**(a) 截图的作用是证明"EDH 真的打开了窗口且处于期望状态"，不是证明"界面好看"。**
本 Phase 的目标（`spec.md:14`）是"在真机 VS Code Extension Development Host 中跑完『启动 → 新建会话 → 一次 prompt → 一次审批 → 一次 Diff』，逐步产出稳定命名的截图与可程序化判定的状态 JSON"。截图服务于**链路连通性判定**。

**(b) AC-26 明确不判画面内容。**
`spec.md:295` 原文：**"AC-26 只要求「5 张截图 + 稳定命名 + 合法 PNG + 被 ignore」，不判画面内容"**。

**(c) 截图判据是程序化的文件级属性，与视觉无关。**
`spec.md:187`（AC-26 验证方式）与 `spec.md:304`（修订段 R2）确定的判据为：张数、稳定文件名（`step-<n>-<name>.png`）、PNG magic bytes + 文件大小下限、仓库根 `.gitignore` 命中、**同一次运行内不同 md5 数 ≥ 2**。全部是文件级/字节级断言，**没有一条涉及色值、间距、字体、布局或状态呈现**。

**(d) UI 自动化被 spec 明令禁止。**
`spec.md:185`：断言驱动扩展源码"**不出现** UI 自动化（`xdotool` 等）引用"；`spec.md:207`（AD-6）重申"**禁止**引入 UI 自动化"。本 Phase 通过命令白名单（`dsh.test.*`）驱动，而非模拟用户视觉操作。

**(e) R2 修订恰恰说明截图内容不被当作视觉证据。**
`spec.md:296` 记录：`reuse` 模式下 5 张截图"均为 3840×1080 桌面壁纸，md5 全同"，"**不构成任何界面证据**"。若截图被当作视觉交付物，其判据应当是"画面是否呈现了目标界面"；而实际修订方向是引入 md5 多样性判据 —— 这从反面确认了本 Phase 审查的是"截图是否真实产生且互不相同"，而非"截图里画了什么"。

### 结论

**不得**因「本 Phase 确实产出了截图」而将本视角升级为适用。截图的存在属于 AC-26 的产出义务，不改变 DAG 中 `ui: false` 的定性，也不产生任何可对照的冻结 token 或界面契约。

即使转为 UI Phase，**现有 5 张 `step-*.png` 也不能直接充当视觉证据**：

- `reuse` 模式产出的是**桌面壁纸**（`spec.md:296`），与界面无关；

→ 转为 UI Phase 时需**重新设计截图采集方案**（至少需支持指定 viewport 尺寸、隔离 Webview 区域、按状态触发出图），并走 **UI Phase 原型确认门禁** 后才能派发本视角。
