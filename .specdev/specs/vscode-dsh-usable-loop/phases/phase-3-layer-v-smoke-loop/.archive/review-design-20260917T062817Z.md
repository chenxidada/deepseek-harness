## D. 重点判断题：`runNodeEnvironmentConstruction()` 与 AD-15 沙箱不变量

**结论（一句话）：相容** —— 它在**沙箱内的扩展宿主 user-data-dir** 里改用户级设置 `dsh.nodeBin`（不是宿主的真实 profile、也不写仓库任何文件），且改后**经 re-read 校验才允许继续**；未触犯 AD-15 的「零仓库改动 / 真实 `~/.dsh` 零写入」，也未越过「驱动职责」的边界。

1. **改的是哪一级、写到哪**：`extension.cjs:1944` `vscode.workspace.getConfiguration('dsh')`，`:1946` `target = vscode.ConfigurationTarget?.Global ?? true`，`:1959` `configuration.update('nodeBin', construction.path, target)`。`Global` 的落点是**当前扩展宿主的 user-data-dir**，即本轮的 `mktemp` 沙箱 → 与壳预置的是**同一个键、同一个文件**。**实证**：壳把合格 Node 预写进 `${USER_DATA_DIR}/User/settings.json`，而构造读到的 `original` 正是该值（真机 `settingRestoredTo = /usr/local/n/versions/node/24.3.0/bin/node`），且改后产品解析链确实取到不合格路径（记录 `source:"vscode-setting"` + `resolvedExecutable` = v20 绝对路径）→ 产品读写的用户级文件就是沙箱内那一个。
2. **是否写穿宿主**：**结构上不可能** —— 宿主进程同时带 `--user-data-dir=<沙箱>` 与 `HOME=<沙箱>`（route A），VS Code 的用户设置文件由前者决定、HOME 又兜住 `~/.config` 路径。**边界声明**：我**未**直接读取宿主 `~/.config/Code/User/settings.json`（该文件在仓库之外，本次只读审查范围内的自动审查也拒绝了这步读取）→ 本条结论建立在「UD + HOME 双沙箱」的结构论证与 `original` 值证据上，而非直接观测该文件。
3. **AD-15 route A 不变量**：「零仓库改动」= 构造不写仓库内任何文件（只写沙箱 UD 内的设置文件）；「真实 `~/.dsh` 零写入」= 构造不触 `~/.dsh`，且脚本既有的真实 `~/.dsh` 摘要断言未变（`realDshHomeUntouched` 证据仍在）→ **相容**。
4. **AC-6a（启动窗口 / 重试预算）与 AD-16（每步前沙箱产品状态为空）**：构造只消耗一次**手工**尝试（真机 `startSnapshot.lastReason: "manual-retry"`、构造前后 `autoRetryUsed: false`），而链路的断线重试**仍拿到了**它的预算（真机 `postLink.disconnect.autoRetryUsed: true`）→ 未吃掉 AC-6a 的预算；构造的失败是**握手前的预检拒绝**，不产生会话/存储，故 AD-16 的「每步起态为空」不受影响（真机 `cleanStateChecks` 段存在、`failedStep: null`）。
5. **属驱动职责还是产品面越界**：**驱动职责**。它只用两个既有公开面——允许集内的 `dsh.test.requestStart`（`spec.md:146`）与 VS Code **配置 API**（`spec.md:116`/`:151` 的约束对象是**命令**，配置 API 不在其内，壳本来就靠**同一个键**锁定子进程 Node）；它不改 `kind` 词表、不加字段、不加记录面、不新增命令，还原失败还会 fail loud。构造代码位于驱动扩展内，不进入产品构建。
6. **还原可靠性**：`finally` 必走 `restoreNodeBinSetting`（`:2045`），其实现先 `update` 再 **re-read 比对**，不一致即以 `harnessError('node-construction-setting-not-restored')`（`:2051`）从 `finally` 抛出 → **任何带 `settingRestoredTo` 的成功结果都蕴含还原已被验证**。

**若判为架构层面不妥我会给的替代方案（本轮不适用）**：① 不构造，改按 `scope-amendment-01:70`（R1.4）走「结构不可得」升级，请用户裁定 AC-13/AC-14 口径变更 —— 会给用户增加一次口径决策并放弃 `spec.md:196` 的既有子句；② 由壳在启动前预置不合格值并**单独拉起一次 EDH** —— 成本是一轮完整宿主启动，且与「宿主无合格 Node 即 `HARNESS_ERROR`」的前置判定纠缠，更难证明「失败来自设置项而非宿主环境」。两者都比现值更贵或更弱 → **维持现值**，仅建议补一条台账（**🟢-1**… 见 🟢-2）。
