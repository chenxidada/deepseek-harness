## 关键发现

### 🔴 Must-Fix

### 🟡 Should-Fix

**🟡-1 — The "契约完整性用例" is delivered as four cases instead of one (`spec.md:63`).**
`spec.md:63` requires a **single** case asserting (a) exactly 18 fields, (b) per-field type + nullability against the design list, (c) `schemaVersion === 1` sourced from `HOST_DIAGNOSTIC_SCHEMA_VERSION`, (d) no text-rendering field. What exists is one `describe` block whose four assertions are split across `host-diagnostics.spec.ts:114` ((a)+(b)), `:147`, `:160` ((c)) and `:171` ((d)).
Evidence: reading `:113-178` — the case at `:114` never mentions `schemaVersion` or the text-field list; the constant/literal assertion lives only at `:166-168`.
Impact: verification power is **not** reduced (each assertion still fails independently for the same drift — adding a field breaks `:128`, bumping the constant breaks `:166`, renaming the version breaks `:167`); the gap is the atomicity the spec asked for, i.e. one case a reader or a Phase-3 driver can cite as "the 18-field contract".
Suggested fix: add the `schemaVersion`/constant assertions and the `TEXT_RENDER_FIELDS` negative to the case at `:114` (or merge `:160`/`:171` into it), keeping the extra cases if useful.

**🟡-2 — The mandated reverse boundary "stderr fewer than 20 lines is recorded as-is" has no assertion.**
`spec.md:61` lists "stderr 少于 20 行时按实际行数记录（不得伪造 20 行）" among the cases that 必须全部存在. The AC-17 case exercises 25 lines (`session-host.spec.ts:316-343`); the AC-18 cases pass `FAKE_STDERR_LINES: '1'` (`:351`, `:365`) but never assert `stderrTail`, and no other case asserts a short tail.
Evidence that the code is nevertheless correct: `host-diagnostics.ts:347` copies `input.stderrTail ?? []` element-wise and nothing in the recorder pads, truncates or fabricates lines, so a 1-line tail stays 1 line (the "keeps the store bounded" case incidentally pins `stderrTail: ['kept']` at `host-diagnostics.spec.ts:360`).
Suggested fix: assert `record.stderrTail` equals the single marker line in the exit-code branch of AC-18, or add a dedicated case.

**🟡-3 — The "child exits with code 0" instance of the AC-18 boundary list is not exercised.**
`spec.md:61` requires "子进程正常退出码 0 后断线（记录 `kind === 'child-exited'`）与 spawn 失败（`kind === 'spawn'`）必须归为不同 kind". The **kind distinction is covered** (`child-exited` at `session-host.spec.ts:329`, `:355`, `:369` vs `spawn` at `:259`), but every exercised death carries a non-zero code: the AC-17/AC-20 cases use the fixture default, and `apps/vscode-dsh/tests/fixtures/fake-sdk-runtime.mjs:256` collapses both "unset" and `0` to exit code `1`, so exit code `0` cannot be produced by the current knob at all.
Evidence that the code is nevertheless correct: `session-host.ts:159` omits `exitCode` only when it is exactly `null`, so a real `0` is recorded as `0` (`host-diagnostics.ts:344`, `input.exitCode ?? null` preserves `0`).
Suggested fix: let the fixture pass a requested `FAKE_EXIT_CODE: '0'` through verbatim and assert `exitCode === 0` with `kind === 'child-exited'`; or record in `implementation.md` why the `0` instance is unreachable through the fake runtime and therefore asserted by inspection.

**🟡-4 — AC-18's post-connect child exit produces no diagnostic record, and the decision is not recorded.**
The only production record site is `session-host.ts:451`, i.e. `start()`'s catch (confirmed by `rg -n "diagnostics\?\." apps/vscode-dsh/src/session-host.ts` → `:377`, `:440`, `:451` only); `onTransportDeath` does not record. So a child that exits **after** a successful handshake produces no `child-exited` record, while AC-18's literal wording ("当子进程退出时") does not distinguish pre- from post-handshake.
This reading is the one `repo-exploration.md` §7.2 recommended, and it satisfies `spec.md:52`'s verification method (both branches driven through a failing start) and `spec.md:54` (which enumerates only start-failure kinds). The gap is that §7.2 required the mapping decision to be "made **explicitly** and recorded" and `implementation.md` §8 records no such item (`rg -n "onTransportDeath|post-connect|握手后" implementation.md` → no match). `implementation.md` §8.7 documents the neighbouring `StartHostPort` fallback decision, so this is an omission rather than a concealment.
Suggested fix: add one line to `implementation.md` §8 stating that AC-18 is evidenced on the pre-handshake exit path and that a post-connect exit is a `TransportClosedError` on the transport-watcher path with no start-failure record — or, if the user prefers the stricter reading, escalate before this phase closes.

**🟡-5 — Nothing pins the `resolvedExecutable` absolute-path property, and the field doc claims it unconditionally.**
`host-diagnostics.ts:70` documents the field as "Absolute path of the Node executable the Host resolved and spawned", but `resolveNodeExecutableSpec` returns `DSH_NODE_BIN` (`launch.ts:132-135`) and `nodeBinSetting` (`:136-139`) verbatim — only `process.execPath` (`:140-144`) is absolute by construction. So with `dsh.nodeBin` set to `node` or a relative path, a record can carry `resolvedExecutable === 'node'` and still satisfy every Phase-2 assertion, because the AC-14 case supplies an absolute path itself and asserts equality with that input rather than with an absolutised value (`session-host.spec.ts:236-238`, `:260`; the SDK-layer case likewise pins `details.executable` to the verbatim `command` it passed, `sdk-client.spec.ts:406-422`). The recorder does not normalise it either (`host-diagnostics.ts:338` redacts and maps `''` to `null` only), and `rg -n "process-exec-path" apps/vscode-dsh/src/host-diagnostics.ts` returns no match — the three-source caveat `implementation.md` §7/F-3.3 relies on is absent from the contract that downstream readers see.
Impact: `spec.md:57` requires the Phase-3 real-machine evidence to contain a `node-environment` record whose `resolvedExecutable` is an absolute path. That property holds for the default source but is guaranteed by no code path or case for the other two, so the Phase-3 assertion is only safe while the default source is in play — which neither the contract nor a test states.
Suggested fix: write the caveat into the field JSDoc and `HostDiagnosticInput`'s counterpart (`host-diagnostics.ts:70`, `:104`) where the contract lives, and add a case that pins the guarantee that does hold (a `process-exec-path` resolution produces an absolute `resolvedExecutable`). Re-deciding F-3.3 to normalise the two caller-supplied sources instead would change `launch.ts` behaviour and belongs to the design track rather than to this fix.

### 🟢 Observations

- **🟢-1 A successful retry appends no "after" record.** `onStartSucceeded()` (`host-diagnostics.ts:320-322`) only closes the chain; the paired addition exists only when the retry itself fails. This matches `spec.md:56`'s verification method (which drives a failing retry) and `host-diagnostics.spec.ts:966-1004` / `:326-343`, and a successful start is not a failure record — noted so the interpretation is explicit rather than accidental.
- **🟢-2 The `bridge-listen` stage window includes one synchronous call.** `stage = 'bridge-listen'` is set before `await bridge.listen(...)` and advanced only after `buildIdeChildEnv(...)` returns (`session-host.ts:413-420`), so a throw from `buildIdeChildEnv` would be labelled `bridge-listen` with a socket path. Env assembly does not throw in practice, so the risk is nil; the stage comment could name the window it actually covers.
- **🟢-3 `records()` is a shallow copy.** The array is copied (`host-diagnostics.ts:364-365`) but the record objects are shared, so the JSDoc "mutating it cannot reach the store" holds only for the array itself. The element type is `readonly`, so no caller in the change set can realistically mutate one; the doc wording could be tightened.
- **🟢-4 The contract table is compared against the design list, but one direction is unchecked.** `expectFieldShape` rejects `null` on a declared non-nullable field (the useful direction). A nullable field that always yields `null` would pass; the design already declares which fields are nullable, so this is a minor residual.
