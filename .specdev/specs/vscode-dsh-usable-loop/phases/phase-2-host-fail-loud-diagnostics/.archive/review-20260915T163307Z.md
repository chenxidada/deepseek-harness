## Must-Fix 汇总

> 2 项，均经调度者独立复核（非采信子 Agent 结论）：MF-1 读三处冻结契约与实现源码对照；C-1 读 guard 源码并追 `runStart` 状态迁移。

### 🔴 MF-1（design）— `HostDiagnosticRecord.kind` 成员词表比冻结契约多 1 个，且契约用例期望值来自实现

- 实现：`apps/vscode-dsh/src/host-diagnostics.ts:33-41` 定义 **8** 个成员（含 `invalid-setting`）。
- 冻结契约：`design.md:307`、`design-zh.md:308`、`repo-exploration.md:78` 与其字段表均为 **7** 个。
- 加重情节：(a) 契约完整性用例把实现的第 8 个成员**内联为期望值**（`apps/vscode-dsh/tests/host-diagnostics.spec.ts:55-69`），违反 `spec.md:63(b)`「以**设计清单**为期望值逐字段比对，不以实现类型推断」；(b) `implementation.md:123` 自陈「无类型变更」与事实不符；(c) `implementation.md` §8 未登记该偏离。
- **裁定（调度者，方案 A′）**：**收窄回 7 个成员，`design.md` 一个字不改。** 依据：该 7 个成员**恰好等于 6 个被 AC 点名的边界 + 1 个兜底**（`other`），而 `invalid-setting` 在 `requirements.md` 中**无任何 AC 覆盖**；它属 `StartErrorKind`（另一类型，Phase 1 引入），由 Phase 1 的 fail-loud 路径承担其根因文案，两个类型不必同构。
- **F-3.1 仍然满足**：反向映射保留**显式** `case 'invalid-setting': return null` 并写明理由 —— 是「显式处理」，不是「落进兜底」。
- **覆盖不得丢失（A′ 的必要组成）**：收窄后 `invalid-setting` 将不再产生诊断记录，而 Extension catch 现行启发式 `!(error instanceof HostStartError)`（`extension.ts:2358-2362`）会继续跳过它，形成覆盖空洞。修法：去掉该启发式，只保留精确信号 `diagnostics.lastSeq() === seqBeforeStart`（`extension.ts:2331` / `:2366`）—— 真 Host 边界失败因 Host 已记录而使高水位线推进（AC-22 不重复计数），未推进者则由 Extension 记一条 `kind: 'other'`。
- 编译期影响面：3 个 `Record<HostFailureKind, …>`（`host-diagnostics.ts:168` / `:180` / `:197`）由编译器兜住，不会漏改。

### 🔴 C-1（connectivity）— 重试 →「追加记录」这条边在 orchestrator 自有失败类上断裂

- 位置：`apps/vscode-dsh/src/host-diagnostics.ts:257-274`，`recorded` guard 的**唯一**清除点是 `:263` 的 `state === 'started'`。
- 现象：`missing-credentials` / `invalid-setting` 是**启动前拒绝**（`auto-start-orchestrator.ts:214-219`，`port.start` 从未进入），**永远到不了 `started`** → 重试时 `kind` 与 `errorMessage` 完全相同 → 签名相同 → `:269-271` 抑制 → **每次重试 0 条记录**，永不产生 `phase === 'retry'` + `retryOfSeq` 配对。
- 讽刺点：`spec.md:56`（AC-22(c)）要求提供可点击重试入口的那个状态（`missing-credentials`）正是该记录边失效的状态。
- 现有用例为何漏掉：AC-22 用例（`host-diagnostics.spec.ts:966`、`:984-1003`）驱动的是 Host 自有类 `node-environment`，走 `:266` 的 `kind === null` 提前返回，**结构上永不触及该 guard**。
- 兜底为何兜不住：`extension.ts:2357-2362` 的 `kind: 'other'` 兜底位于 `port.start` 的 catch 内，而 `:214` 的抛出发生在其之前。
- **裁定（调度者）**：guard 生命周期收窄到**单次尝试** —— 任何离开 `failed` 的转移都重新武装。`runStart` 必在任何失败前设置 `'starting'` 并 `notify()`（`auto-start-orchestrator.ts:205-207`），故重试必然重新武装；同一次尝试内 `:241`/`:249` 两次 notify 均在该 `'starting'` **之后**，签名相同仍被抑制 → 尝试内去重语义不变。
- 连通性审查已声明该条为**代码追踪结论**（其一次性探针被环境拦截，无运行期证据）；调度者已独立追 `runStart` 状态迁移予以确认。**修完后必须补一条扩展级用例**：`missing-credentials` 态触发重试 → 断言记录数 1 → 2 且第二条 `phase === 'retry'`、`retryOfSeq` 指向首条。

## 严重度裁定（调度者）—— C-2「握手后退出」的两次审查分歧

`review-connectivity.md` 的**重跑版**（同角色、同代码、00:10 落盘）把 C-2 从 SHOULD-FIX 升为 🔴 Must-Fix；而**原件**（`.archive/review-connectivity-20260915T160437Z.md`，本报告合并所据）与 `review-correctness.md` 🟡-4 均判非阻塞。两个视角对 `spec.md:61` 同一句话的读法冲突，调度者裁定如下（依据 `spec.md` 全文，非采信任一报告）：

- **范围证据支持「握手前」读法**：`spec.md:13` 把整个 AC 集的范围明确限定为「Host **启动**的每个失败边界」—— 一次**握手后**的死亡不是启动失败边界，而是运行期断线；`spec.md:52`（AC-18 的验证方式）用 `process.exit(7)` / SIGTERM 驱动，落在启动窗口内；`HostDiagnosticRecord.phase` 的词表只有 `'start' | 'retry'`，本就以启动为中心设计，反证握手后事件不属于该记录。
- `spec.md:61` 的「子进程正常退出码 0 后断线（记录 `kind === 'child-exited'`）…必须归为不同 kind」在**握手前**读法下**可被字面满足**：只需 fixture 原样透传 `FAKE_EXIT_CODE: '0'`（见 SF-10），无需新增记录边。
- `repo-exploration.md:123` 提出第二插入点后，其 §8.1 要求的是「**显式裁定**」而非「必须接线」—— 因此缺的不是功能，而是**决策留痕**。
- **裁定 = A + D**：按握手前读法取证（SF-10）；把该取舍**显式写入** `implementation.md` §8（SF-11）；**并**将「握手后死亡在诊断通道不可见」登记到 `tech-debt-registry.md`，避免 Phase 3 真机运行把空通道读作「没有发生失败」（此即重跑 C-2 自己指出的风险）。
- **不采纳接线方案的理由**：需给 `phase` 加第三成员（属字段面改动，按 AD-14 决策 11 必须递增 `schemaVersion`，会连带破坏 Phase 3 既有断言分流），或语义错用 `'start'`；代价与收益不成比例，且超出本 Phase 设计范围。

> 声明：本裁定**不隐藏**任何 🔴 —— 重跑报告的 C-2 仍以 🔴 形式存于 `review-connectivity.md`（各视角原始报告不得改写）；本节说明调度者为何未将其计入本报告的 Must-Fix 汇总，以及它被转化为何种可验收动作。
