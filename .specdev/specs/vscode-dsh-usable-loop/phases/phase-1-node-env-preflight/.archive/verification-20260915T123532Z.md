## 4. Reviewer-handover items (6)

**1. N1 — AC-1(b).** The automated case at `node-env-guard.spec.ts:449-461` validates `process.execPath`, not the spec's literal step of locating the pinned release in the three roots; the review is correct. My independent judgement: this is a **verification-method gap, not a product-behaviour gap**. The (b) sentence describes a host fact ("the pinned release is what runs the gate"), not a product behaviour; welding `report.version === '24.3.0'` into a unit test would make the suite fail on any machine without that exact install, which is the outcome the review warned against and I agree with. I therefore executed the literal step myself: `/usr/local/n/versions/node/24.3.0/bin/node` and `/usr/local/bin/node` are both version 24.3.0 and both pass the shipped gate with `ok:true`; `~/.nvm/...` has no such release. AC-1(b) is achieved on this host, and the missing automation is recorded in §6 as a MEDIUM residual risk.

**2. D-1 — review-item codes.** Verified present in the current tree, so D-1 stands unfixed: `node-env-guard.spec.ts:240` `(S9)`, `:629` `(S5, AD-9)`, `:664` `// M2:`, and `auto-start-orchestrator.spec.ts:144` `(AC-9, AD-4, M2)`. These are review-history traces in shipped comments and conflict with `AGENTS.md:144`. The `AD-*` references are **not** wrongly deleted — `AD-9` and `AD-4` are still present and are legitimate `design.md` decision ids, matching the existing convention (`session-host.ts:106`, `extension.ts:2173`). Correct remediation is to drop the `S*` / `M*` codes and keep the `AD-*` ids. No AC depends on this.

**3. D-2 — non-string `dsh.nodeBin` classifies as `process-failed`.** Reproduced independently and the chain is confirmed by reading the source: `readNodeBinSetting` throws a bare `Error` with no `kind` (`extension.ts:2183-2187`, inside `createStartHostPort`'s `start()` at `:2253`) → `AutoStartOrchestrator` normalises an absent `kind` to `process-failed` (`auto-start-orchestrator.ts:230`). Observed in the real activation: `errorKind='process-failed'`, message `dsh.nodeBin must be a path to a Node.js executable string, got number`. My judgement: **not an AC-9 deviation.** AC-9 classifies Node-environment failures (`missing`, `not-executable`, `missing-apis`), all three of which do reach `node-environment`; a hand-edited non-string setting is a different failure that never enters the pre-flight, and the manifest declares `type: "string"` so the settings UI cannot produce it. The behaviour is still fail-loud with a specific, user-visible message. Recorded as an open SHOULD-FIX with LOW severity, not as an AC failure.

**4. AC-10(f) cross-Phase dependency — registered.** Verbatim: **the AC-10 real-machine consumption branch is evidenced by Phase 3 (cross-Phase dependency)**. Phase 1's verdict scope is AC-10 (a)–(e) only; Phase 1 is not failed for this, and this report does **not** claim the real-machine branch was verified. If Phase 3's supplementary row fails, the whole of AC-10 fails.

**5. M2 falsifiability — done, assertion upgraded to VERIFIED.** Two independent observations, neither of them the correctness reviewer's blocked probe. (i) End to end through the real extension: an invalid Node named by the setting produces snapshot `errorKind='node-environment'` (scenario 7). **6. `HostStartError.diagnostic` is a Phase 2 surface — registered, not a failure.** Phase 1 needs `kind` plus the five-line message; the structured `diagnostic` carrier is unused for Phase 1's own flow.
