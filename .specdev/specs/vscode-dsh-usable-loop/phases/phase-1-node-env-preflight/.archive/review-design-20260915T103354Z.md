## Must-Fix (🔴)

**M1 — AC-3(d) "every local-environment entry carries a concrete command" fails on exactly one entry, in both languages.**

- Evidence: `docs/development.md:131` — `- Reload the window after changing either input; the extension reads the setting on every start and does not cache it.` and `docs/development.zh.md:136` — `- 改动任一输入后请重新加载窗口；扩展在每次启动时重新读取设置项，不缓存。`
- The other five local-environment entries carry a command token (`node --version` at `:123`/`:128`, `nvm use` / `n 24.3.0` at `:124`/`:129`, `export PATH=` at `:125`/`:130`, the setting id `dsh.nodeBin` and `DSH_NODE_BIN` at `:129`/`:134`, `<node path> --version` at `:130`/`:135`). The reload entry contains none of the tokens AC-3's verification names (`nvm` / `n` / `export DSH_NODE_BIN=` / `PATH=` / VS Code setting id), and AC-3's own text requires "「本机环境侧职责」列出开发者本机需要执行的步骤及其 **具体命令**".
- Why this is a must-fix and not a wording nit: `spec.md:45` states AC-3's verification as a per-entry assertion — "「本机环境侧职责」每条都含具体命令" — and the phase's acceptance is "逐条验证策略全部通过" (`phase-plan.md` Phase 1 验收). As written, one entry cannot satisfy that assertion, so AC-3 cannot be judged PASS without either the entry or the assertion changing; `spec.md:28`'s "两张清单中必须不出现无法判定完成与否的条目" is a separate clause and does not cover this one (the reload step is decidable, it just has no command).
- Smallest fix: name the command in each language (for example `Developer: Reload Window` / `Developer: Reload Window（命令面板）`), or state the reload action as a step whose command is spelled out. If instead the phase intends the assertion to be relaxed, that is a spec change and cannot be decided inside Phase 1.
- Note for the merge: this is the only 🔴 I raise; `reviewer-correctness` owns the AC-coverage call, but the evidence above is checkable and independent of implementation behavior.

## Should-Fix (🟡)

**S1 — Two additive manifest keys are not recorded in the deviation chapter (constitution §6.2).**
`apps/vscode-dsh/package.json:63` adds `"scope": "machine-overridable"` and `:65` adds `"markdownDescription"`; `implementation.md` §4 records only `title` (deviation 8). `spec.md:53` AC-10(a) requires type, default and a non-empty `description`, and AD-9's 设置项契约 table (`design.md:230-237`) lists only id/type/default/description. Both additions are defensible (`machine-overridable` matches "read per start, per machine"; `markdownDescription` mirrors `description` verbatim), but constitution §6.2 requires spec-inconsistent implementation to be recorded, so §4 should gain this line — or the keys should be dropped if unintended.

**S2 — The "no caching" clause has static evidence only, and the test that claims it cannot falsify caching.**
`apps/vscode-dsh/tests/node-env-guard.spec.ts:455` is titled "reads the setting and passes it to the session host on every start" but performs exactly one `dsh.test.requestStart` (`:470`) and asserts `starts` has length 1 (`:474`). A single start cannot distinguish "re-read" from "cached". AD-9's 取舍 (`design.md:241`) and `spec.md:112` make "每次 Host 启动重新读取，不缓存跨启动结果" a named requirement, and the user's review brief asks for it specifically. The implementation does satisfy it statically (`apps/vscode-dsh/src/extension.ts:2253` is inside the per-start function, and no module-level cache exists), so this is an evidence/title gap: either add a two-start case that changes the returned value between starts, or retitle the case to what it proves.

**S3 — AC-3's structural assertions are not implemented anywhere in the phase's tests; their falsifiability depends entirely on the verifier's grep.**
The only test that names AC-3, `apps/vscode-dsh/tests/node-env-guard.spec.ts:361`, asserts only that both docs contain `.nvmrc`, the pinned version, `DSH_NODE_BIN` and `dsh.nodeBin` (`:365-368`). AC-3's verification (a) and (b) — "两张清单标题存在" and "两个子清单标题存在…删除任一子清单标题必须导致 (b) 失败" — are not asserted there. My own check shows the four label strings are unique in each file (`grep -c` = 1 for `Repository-side responsibilities` / `Local-environment responsibilities` / `Terminal side` / `Extension subprocess side` in `docs/development.md`, and for `仓库侧职责` / `本机环境侧职责` / `终端侧` / `扩展子进程侧` in `docs/development.zh.md`), so text matching is feasible and the deletion falsification does hold — but it will only hold if `verification.md` records the exact text-based assertion it ran. Recommend the verifier paste the four `grep -F` counts (1 before deletion, 0 after a simulated deletion) into `verification.md`, and consider a small test in the phase's own suite that asserts the four labels in both files.

**S4 — The doc says the floor is "declared once", while the app re-declares the literal.**
`docs/development.md:105` ("The floor is declared once as `engines.node` in the root `package.json`") and `docs/development.zh.md:110` are in tension with `apps/vscode-dsh/src/node-env-guard.ts:18` `EXPECTED_NODE_RANGE = '^22.19.0 || >=24.0.0'`, a second copy of the same range. The copy is pinned equal to the manifest by `apps/vscode-dsh/tests/node-env-guard.spec.ts:342-345`, so it cannot silently drift, and `spec.md:110` requires such a constant to render the diagnostic — the fix is wording ("declared once as `engines.node` in the root `package.json`, and copied into the pre-flight constant") rather than code.

**S5 — The routing decision (setting → Host, resolved object → `HarnessClient`) is a deviation from AD-9's literal wording and is not recorded.**
`design.md:238` says the extension passes the value as an explicit input "传给 `HarnessClient`", while the implementation passes `nodeBinSetting` to `IdeSessionHost.start()` (`apps/vscode-dsh/src/extension.ts:2256`) and the Host passes the resolved `nodeExecutable` to `HarnessClient` (`apps/vscode-dsh/src/session-host.ts:295`). AC-10(e) explicitly accepts the Host-options routing (`spec.md:53`), and AD-1's shared-object invariant forces the Host to be the resolver, so the implementation is right and the design sentence is imprecise → class ①, not a violation. Still worth one line in `implementation.md` §4 so the next reader does not read it as drift.
